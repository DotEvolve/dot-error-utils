# Requirements Document

## Introduction

This feature integrates `@dotevolve/error-utils` extensively and consistently across all three application repositories in the floorix workspace:

- **floorix-api** — Express.js backend API (Node.js)
- **floorix-admin** — React + Vite super-admin frontend
- **floorix-app** — React + Vite factory-operator frontend

The goal is to eliminate all generic error handling, ensure every error is captured in Sentry via `@dotevolve/error-utils`, and enforce a consistent, typed error model across the entire platform. The `@dotevolve/error-utils` package provides typed error classes (`AppError`, `ValidationError`, `AuthenticationError`, `AuthorizationError`, `NotFoundError`, `ConflictError`), Express middleware (`setupSentryMiddleware`, `correlationIdMiddleware`, `setupSentryErrorHandler`, `asyncHandler`), Sentry initialisation helpers (`initializeSentry`, `initializeReactSentry`), and a Prisma transaction wrapper (`withTransaction`).

---

## Glossary

- **API**: The `floorix-api` Express.js backend service.
- **Admin**: The `floorix-admin` React frontend (super-admin dashboard).
- **Client**: The `floorix-app` React frontend (factory-operator interface).
- **error-utils**: The `@dotevolve/error-utils` npm package providing shared error handling utilities.
- **AppError**: The base typed error class exported by error-utils.
- **Typed_Error**: Any of the specific error classes exported by error-utils: `ValidationError`, `AuthenticationError`, `AuthorizationError`, `NotFoundError`, `ConflictError`, or `AppError`.
- **Generic_Error**: A plain `Error`, `catch (err) { res.status(500).json(...) }`, or any error handling that does not use a Typed_Error class.
- **asyncHandler**: The `asyncHandler` wrapper exported by `@dotevolve/error-utils/express` that catches promise rejections in Express route handlers.
- **Sentry**: The error monitoring service used across all repos.
- **Correlation_ID**: A unique request identifier propagated via the `X-Correlation-Id` HTTP header, generated by `correlationIdMiddleware`.
- **Error_Boundary**: A React component (from `@sentry/react`) that catches unhandled render errors and reports them to Sentry.
- **withTransaction**: The Mongoose/Prisma transaction wrapper exported by error-utils that adds Sentry performance monitoring.
- **SENTRY_DSN**: The Sentry Data Source Name environment variable required for Sentry initialisation.

## Requirements

### Requirement 1: API — Sentry Initialisation

**User Story:** As a platform engineer, I want Sentry to be initialised before any other code runs in the API, so that all errors are captured from the moment the process starts.

#### Acceptance Criteria

1. THE API SHALL call `initializeSentry` from `@dotevolve/error-utils/node` as the first statement in the server entry point (`server.ts` or `api/index.ts`), before any Express app setup.
2. WHEN `SENTRY_DSN` is set in the environment, THE API SHALL pass it to `initializeSentry` along with `serviceName: "floorix-api"`, `environment`, and `release`.
3. IF `SENTRY_DSN` is not set in the environment, THEN THE API SHALL log a warning and continue without Sentry capture.

---

### Requirement 2: API — Express Middleware Setup

**User Story:** As a platform engineer, I want the API to use error-utils middleware in the correct order, so that all requests are traced and all errors are handled consistently.

#### Acceptance Criteria

1. THE API SHALL call `setupSentryMiddleware(app)` from `@dotevolve/error-utils/express` as the first middleware registered on the Express app, before body parsers and routes.
2. THE API SHALL register `correlationIdMiddleware` from `@dotevolve/error-utils/express` immediately after `setupSentryMiddleware`.
3. THE API SHALL call `setupSentryErrorHandler(app)` from `@dotevolve/error-utils/express` as the last middleware registered on the Express app, after all routes.
4. WHEN a request is received, THE API SHALL include the `X-Correlation-Id` header in the response.

---

### Requirement 3: API — Typed Error Classes in Route Handlers

**User Story:** As a platform engineer, I want all API route handlers to throw Typed_Errors instead of generic errors, so that error responses are consistent and Sentry captures structured context.

#### Acceptance Criteria

1. THE API SHALL wrap every async route handler with `asyncHandler` from `@dotevolve/error-utils/express`.
2. WHEN a requested resource is not found, THE API SHALL throw a `NotFoundError` with the resource name and identifier.
3. WHEN input validation fails, THE API SHALL throw a `ValidationError` with field-level details.
4. WHEN a request is unauthenticated, THE API SHALL throw an `AuthenticationError`.
5. WHEN a request is unauthorised, THE API SHALL throw an `AuthorizationError`.
6. WHEN a resource conflict occurs (e.g. duplicate slug), THE API SHALL throw a `ConflictError` with a descriptive message.
7. THE API SHALL contain zero instances of `res.status(500).json(...)` or `res.status(4xx).json(...)` outside of the centralised error handler provided by error-utils.
8. THE API SHALL contain zero bare `catch (err) { ... }` blocks in route handlers that manually construct error responses.

---

### Requirement 4: API — Standardised Error Response Format

**User Story:** As a frontend developer, I want all API errors to follow a consistent JSON shape, so that the Admin and Client apps can handle errors uniformly.

#### Acceptance Criteria

1. WHEN THE API returns an error response, THE API SHALL use the format `{ success: false, error: { code, category, message, correlationId }, timestamp }` as produced by the error-utils error handler.
2. WHEN a `ValidationError` is thrown, THE API SHALL include field-level `details` in the error response body.
3. THE API SHALL return HTTP status codes that match the Typed_Error class: 400 for `ValidationError`, 401 for `AuthenticationError`, 403 for `AuthorizationError`, 404 for `NotFoundError`, 409 for `ConflictError`.

---

### Requirement 5: API — Sentry Context Enrichment

**User Story:** As a platform engineer, I want Sentry events from the API to include user and request context, so that errors can be traced back to specific users and requests.

#### Acceptance Criteria

1. WHEN an authenticated request triggers an error, THE API SHALL attach the authenticated user's ID and role to the Sentry event via `attachSentryContext`.
2. WHEN any error is captured, THE API SHALL include the `Correlation_ID` in the Sentry event tags.
3. THE API SHALL NOT capture `ValidationError` events in Sentry, as these are user-input errors and not system errors.

---

### Requirement 6: Admin — Sentry Initialisation

**User Story:** As a platform engineer, I want Sentry to be initialised in the Admin app before the React tree renders, so that all unhandled errors are captured.

#### Acceptance Criteria

1. THE Admin SHALL call `initializeReactSentry` from `@dotevolve/error-utils/react` in `src/lib/sentry.ts` before the React root is mounted.
2. WHEN `VITE_SENTRY_DSN` is set in the environment, THE Admin SHALL pass it to `initializeReactSentry`.
3. THE Admin SHALL import `src/lib/sentry.ts` as the first import in `src/main.tsx`.

---

### Requirement 7: Admin — React Error Boundary

**User Story:** As a platform engineer, I want the Admin app to catch all unhandled render errors with a Sentry Error Boundary, so that crashes are reported and users see a graceful fallback.

#### Acceptance Criteria

1. THE Admin SHALL wrap the root React component tree with `Sentry.ErrorBoundary` from `@sentry/react`.
2. WHEN an unhandled render error occurs, THE Admin SHALL display a user-facing fallback message.
3. WHEN an unhandled render error occurs, THE Admin SHALL capture the error in Sentry automatically via the Error Boundary.

---

### Requirement 8: Admin — Axios Error Handling with Typed Errors

**User Story:** As a platform engineer, I want the Admin Axios interceptor to handle errors using error-utils error classes, so that API errors are consistently classified and reported.

#### Acceptance Criteria

1. WHEN the Admin Axios response interceptor receives a non-401 error response, THE Admin SHALL extract the `correlationId` from the response body and include it in any Sentry capture.
2. WHEN the Admin Axios response interceptor receives a 5xx error, THE Admin SHALL capture the error in Sentry using `Sentry.captureException`.
3. WHEN the Admin Axios response interceptor receives a 401 and the token refresh fails, THE Admin SHALL capture the refresh failure in Sentry before redirecting to `/login`.
4. THE Admin SHALL NOT use `console.error` as the sole error reporting mechanism for API errors.

---

### Requirement 9: Admin — Page-Level Error Handling

**User Story:** As a platform engineer, I want all Admin page components to handle API errors using the standardised error response format, so that error messages are consistent and system errors are reported to Sentry.

#### Acceptance Criteria

1. WHEN an API call in an Admin page component fails with a 5xx status, THE Admin SHALL capture the error in Sentry using `Sentry.captureException`.
2. WHEN an API call in an Admin page component fails with a 4xx status, THE Admin SHALL display the `error.message` from the standardised error response to the user without capturing to Sentry.
3. THE Admin SHALL NOT use bare `catch (err) { setError("An unexpected error occurred") }` blocks that discard error context.

---

### Requirement 10: Client — Sentry Initialisation

**User Story:** As a platform engineer, I want Sentry to be initialised in the Client app before the React tree renders, so that all unhandled errors are captured.

#### Acceptance Criteria

1. THE Client SHALL call `initializeReactSentry` from `@dotevolve/error-utils/react` in a dedicated `src/lib/sentry.ts` file.
2. WHEN `VITE_SENTRY_DSN` is set in the environment, THE Client SHALL pass it to `initializeReactSentry` with `environment` and `tracesSampleRate`.
3. THE Client SHALL import `src/lib/sentry.ts` as the first import in `src/index.tsx`.

---

### Requirement 11: Client — React Error Boundary

**User Story:** As a platform engineer, I want the Client app to catch all unhandled render errors with a Sentry Error Boundary, so that crashes are reported and factory operators see a graceful fallback.

#### Acceptance Criteria

1. THE Client SHALL wrap the root React component tree with `Sentry.ErrorBoundary` from `@sentry/react`.
2. WHEN an unhandled render error occurs, THE Client SHALL display a user-facing fallback message appropriate for factory operators.
3. WHEN an unhandled render error occurs, THE Client SHALL capture the error in Sentry automatically via the Error Boundary.

---

### Requirement 12: Client — Axios Error Handling

**User Story:** As a platform engineer, I want the Client Axios interceptor to report errors to Sentry, so that API failures in the factory operator interface are tracked.

#### Acceptance Criteria

1. WHEN the Client Axios response interceptor receives a 5xx error, THE Client SHALL capture the error in Sentry using `Sentry.captureException`.
2. WHEN the Client Axios response interceptor receives a 401 and the user is redirected to `/login`, THE Client SHALL capture the session expiry event in Sentry as a breadcrumb.
3. THE Client SHALL NOT use `console.error` as the sole error reporting mechanism for API errors.

---

### Requirement 13: Client — Redux Thunk Error Handling

**User Story:** As a platform engineer, I want Redux async thunks in the Client app to report errors to Sentry, so that login and data-fetching failures are tracked.

#### Acceptance Criteria

1. WHEN the `loginUser` thunk in `UserSlice` catches an error, THE Client SHALL capture the error in Sentry using `Sentry.captureException` before dispatching the rejected action.
2. WHEN any async thunk catches an unexpected error (non-4xx), THE Client SHALL capture the error in Sentry.
3. THE Client SHALL NOT swallow errors in thunks without reporting them to Sentry.

---

### Requirement 14: Client — Dashboard Component Error Handling

**User Story:** As a platform engineer, I want all Client dashboard components to handle API errors consistently, so that factory operators see meaningful messages and system errors are tracked.

#### Acceptance Criteria

1. WHEN an API call in a Client dashboard component fails with a 5xx status, THE Client SHALL capture the error in Sentry using `Sentry.captureException`.
2. WHEN an API call in a Client dashboard component fails with a 4xx status, THE Client SHALL display the `error.message` from the standardised API error response to the user.
3. THE Client SHALL NOT use bare `catch (err) { console.error(err) }` blocks that discard error context without Sentry capture.

---

### Requirement 15: Cross-Repo — No Generic Error Handling

**User Story:** As a platform engineer, I want zero instances of generic error handling across all repos, so that every error is classified, structured, and observable.

#### Acceptance Criteria

1. THE API SHALL contain zero route handlers that use `new Error(...)` to construct HTTP error responses.
2. THE API SHALL contain zero `catch` blocks that call `next(err)` with a plain `Error` object instead of a Typed_Error.
3. THE Admin SHALL contain zero `catch` blocks that call `setError("An unexpected error occurred")` without also capturing to Sentry.
4. THE Client SHALL contain zero `catch` blocks that call `console.error` as the only error handling action.
5. WHERE `@dotevolve/error-utils` provides a typed error class for a given error condition, THE API SHALL use that class instead of a generic alternative.

---

### Requirement 16: Cross-Repo — Consistent Package Import Paths

**User Story:** As a platform engineer, I want all repos to import from the correct error-utils subpath, so that bundle sizes are minimised and peer dependency conflicts are avoided.

#### Acceptance Criteria

1. THE API SHALL import error-utils utilities exclusively from `@dotevolve/error-utils/node` or `@dotevolve/error-utils/express`.
2. THE Admin SHALL import error-utils utilities exclusively from `@dotevolve/error-utils/react`.
3. THE Client SHALL import error-utils utilities exclusively from `@dotevolve/error-utils/react`.
4. THE API SHALL NOT import from `@dotevolve/error-utils/react`.
5. THE Admin SHALL NOT import from `@dotevolve/error-utils/node` or `@dotevolve/error-utils/express`.
6. THE Client SHALL NOT import from `@dotevolve/error-utils/node` or `@dotevolve/error-utils/express`.

---

### Requirement 17: Cross-Repo — Environment Variable Configuration

**User Story:** As a platform engineer, I want all repos to have the required Sentry environment variables documented and validated, so that Sentry integration is not silently broken in any environment.

#### Acceptance Criteria

1. THE API SHALL document `SENTRY_DSN`, `NODE_ENV`, and `SENTRY_ENVIRONMENT` as required environment variables in its `config.env` template.
2. THE Admin SHALL document `VITE_SENTRY_DSN` as a required environment variable in its `.env.local` template.
3. THE Client SHALL document `VITE_SENTRY_DSN` as a required environment variable in its `.env` template.
4. WHEN `SENTRY_DSN` or `VITE_SENTRY_DSN` is absent at startup, THE respective service SHALL log a warning indicating that Sentry error capture is disabled.
